# 分阶段 GitHub 发布与 README 设计

## 目标

把 `codex/offline-workbench` 发布为一个可运行、可复现、便于评审的具身智能行业研究工作台仓库，并在 GitHub 上保留从离线 MVP 到在线研究工作流的迭代节点。

## README 设计

README 以中文为主，面向三类读者：希望快速运行项目的协作者、评估项目完整度的面试官或评审者、以及需要理解研究流程边界的早期用户。内容按“先理解产品、再运行项目、最后深入实现”的顺序组织：

1. 一句话定位和当前状态。
2. 问题背景、目标用户和证据优先原则。
3. 端到端工作流：研究任务、七维框架、来源、证据矩阵、候选/正式简报。
4. 功能边界、审核门禁和实时研究的降级策略。
5. 技术架构与核心目录。
6. 本地安装、离线演示、在线 provider 配置和启动方式。
7. 测试、代码质量检查和已知限制。
8. 迭代版本表与项目文档索引。

README 只描述当前分支中已经实现或明确配置的能力；Dify、Tavily 和 OpenAI 等外部服务会标注为可选/需密钥，不把在线研究写成无配置即可用的功能。密钥、SQLite 数据库和本地运行产物不进入版本控制。

## 版本发布策略

保留现有提交历史，并将同一发布分支按功能节点做快进推送。每个节点同时创建一个可识别的 annotated tag：

| 版本 | 历史节点 | 内容 |
| --- | --- | --- |
| `v0.1.0-offline` | `1967e60` | 离线研究工作台、SQLite 存储、证据审核和导出 |
| `v0.2.0-terminal` | `2ad4266` | 研究终端视觉层、KPI、风险队列和五阶段界面 |
| `v0.3.0-online` | `4b695bd` | Tavily 检索、Dify workflow 适配和在线研究运行 |
| `v0.3.1-fallback` | `40e3f33` | provider fallback、超时和错误恢复 |
| `v0.4.0-readme` | README 最终提交 | 完整启动说明、配置说明和版本索引 |

推送顺序必须从旧到新，确保远端分支只做 fast-forward 更新；如果远端已经存在同名分支，先读取其状态并只在能确认是同一历史时继续。README 提交只在所有测试和文档检查通过后创建。

## 验证策略

- 使用现有 `pytest` 测试套件验证领域模型、存储、证据质量、导出、UI 和在线 provider 适配层。
- 使用 `ruff check .` 检查 Python 代码质量。
- 使用脚本检查 README 中列出的文件、命令、环境变量和版本标签与仓库实际内容一致。
- 不在自动化验证中调用真实 Tavily、Dify 或 OpenAI 服务；在线服务仅按项目已有测试的 mock/fallback 路径验证。

## 非目标

本次发布不扩展产品功能、不修改业务逻辑、不引入账号系统或部署平台，也不把草稿 PR、线上部署或真实 provider 调用当作 README 的必要前置条件。
